# Captura 0.0.8 performance pass

Packaged-app latency measured with `script/perf.py` against an isolated test store.
The "Before" numbers are the 0.0.6 release (commit `0e7cb0e`), built in a separate
detached worktree so concurrent source edits could not leak into the baseline.

## Environment

- Machine: MacBook Pro (Mac15,6), Apple M3 Pro, 12 cores, 18 GB
- macOS 27.0.1 (build 26A434), from `sw_vers`
- Baseline commit: `0e7cb0e` ("Prepare Captura 0.0.6 local release"), detached worktree
  at `/private/tmp/captura-baseline`
- Bundle: `pnpm tauri build --bundles app`, signed with the "Captura Dev" identity;
  `codesign --verify --strict --deep` passes
- Python 3.12.12 (stdlib only)
- Load: the 1-minute load average was about 7.4 during the canonical run, and other
  work (including builds in the main worktree) was running at the same time. Absolute
  numbers depend on load, so compare Before and After on a similarly quiet machine.

## Commands

```sh
git -C <main worktree> worktree add --detach /private/tmp/captura-baseline 0e7cb0e
cd /private/tmp/captura-baseline
pnpm install --frozen-lockfile
pnpm tauri build --bundles app
codesign --verify --strict --deep --verbose=2 src-tauri/target/release/bundle/macos/Captura.app
# perf.py is copied in from the main worktree (the canonical copy is script/perf.py there)
python3 script/perf.py \
  --app /private/tmp/captura-baseline/src-tauri/target/release/bundle/macos/Captura.app \
  --work-root /private/tmp/captura-baseline-run
```

For the After run, build the candidate and run the same command with `--app` pointed at
its bundle. The defaults are `--seed 300 --warmups 3 --samples 30 --cold-runs 3`.

Isolation and safety rules:

- The script launches `Contents/MacOS/captura` directly with `CAPTURA_TEST_MODE=1`,
  `CAPTURA_DATA_DIR=<run>/data` and `CAPTURA_QA_DIR=<run>/qa`. In test mode the backup
  goes to `<run>/data.backup` and diagnostics go to `<run>/Logs/Captura/diagnostics.jsonl`.
- It stops only the PID it spawned. It sends the QA `quit` action first, then SIGTERM,
  then SIGKILL to that PID.
- It never uses `script/build_and_run.sh`, because that script runs `pkill -x captura`
  and would also close the user's installed Captura.
- It refuses any work root inside `~/Library`.

## Method

- Interaction timings are taken inside the main WKWebView with `performance.now()`
  and returned through QA `eval`. This avoids the harness's 25 ms request-polling
  steps. WKWebView limits `performance.now()` to 1 ms resolution.
- "2 rAF" means the second `requestAnimationFrame` callback after the change. By then,
  the frame that contains the change has painted.
- Each metric uses 3 warmups and 30 samples. p95 is nearest-rank (the 29th of 30 sorted
  samples).
- Between samples the script waits for 2 rAF plus 40 ms, so leftover renders from
  `captures-changed` events don't carry into the next sample.
- The script turns on `keepOpen` in the isolated store so the panel can't auto-hide
  partway through a run. The show path (`present_main_window`) is the same either way.
- Measurements start once the updater's silent check (3 s after launch) has passed.
- Metrics:
  1. **toggle_item**: `invoke('toggle_item', {id})` on the same short note, toggled
     back and forth. An even number of toggles leaves the note open.
  2. **delete_item**: `invoke('delete_item', {id})` on 33 seeded throwaway captures,
     with the queue going from 333 to 300 rows.
  3. **snapshot_queue**: `invoke('snapshot_queue')` with 300 rows.
  4. **Detail open**: a `dblclick` dispatched on the first `.queue-item` (the 10 KiB
     capture), timed until `.capture-sheet textarea, .capture-sheet [data-capture-preview]`
     exists (seen through a MutationObserver), then 2 rAF. The sheet is closed with
     Escape between samples. The script checks that the full 10 KiB text rendered,
     including the end marker.
  5. **Composer typing**: the 10 KiB string is written into `.quick-capture textarea`
     with the native value setter and an `input` event, then timed to 2 rAF. The
     composer is cleared between samples.
  6. **Warm panel**: `invoke('hide_main_window')`, a 350 ms wait, listeners registered
     for `focus` and `visibilitychange`, then:
     - (a) QA `show` (`present_main_window`), timed from the first of those events to
       2 rAF;
     - (b) the webview calls `invoke('show_main_window')` itself, which also gives a
       time from the show request to 2 rAF with no polling involved.

     `focus` fired first in 33 of 33 samples for both (a) and (b). The app's focus
     listener calls `snapshot_queue` to refresh the queue. The script catches that
     request by wrapping `window.fetch` (Tauri's macOS IPC is `fetch('ipc://localhost/…')`,
     and `__TAURI_INTERNALS__.invoke` is read-only) and reports the time to the reply
     plus 2 rAF. That number is approximate: it does not see React's commit directly.
- **Cold start** is wall time measured in Python from `Popen` until:
  - the first QA `windows` answer (the QA thread is up and the main thread is running
    `run_on_main`). This includes up to 25 ms of polling.
  - the webview's `performance.timeOrigin`.
  - the `startup_probe`, `storage_ready` and `database_open_succeeded` diagnostics
    events, using their `at_utc` timestamps from the isolated
    `<run>/Logs/Captura/diagnostics.jsonl`.

  The first launch uses an empty store. Three relaunches use the seeded store.

## Dataset

A fresh isolated store is seeded through `invoke('create_item')`:

- **33 throwaway notes** (`Perf throwaway N delete me`), created first so they are the
  oldest. They are used and removed by the delete metric.
- **299 short captures**, cycling through three kinds:
  - note: about 75 characters;
  - prompt: about 85 characters;
  - link: `https://example.com/perf/link/N?ref=captura`.
- **One 10 KiB Markdown note** (10,240 bytes of ASCII), created last so it is the first
  row. It has headings, bold and emphasis, inline code, links, lists, block quotes and
  fenced code, and ends with `PERF-END-MARKER`.

All metrics after the delete metric run with 300 captures in the queue (Inbox filter,
all open).

Not measured, or measured only in part:

- **Warm panel time from the native show trigger to `focus`** is not measured for the
  QA `show` path, because the request goes through 25 ms polling. Path (b) covers it
  from inside the webview: the show request reaches `focus` in about 10 ms (the gap between the two medians), and
  "request → 2 rAF" is the end-to-end number.
- **Physical keyboard and pointer latency is not measured.** The events are dispatched
  from script, as in `verify-detail.py`.
- **Cold start has one sample per launch type.** The first seeded relaunch's
  2.8 s webview start is a one-off outlier. The second run's first seeded relaunch
  took 1.16 s to the first `windows` answer.

## Observations for the optimization pass (not acted on here)

These are read from the 0.0.6 source and match the numbers above:

- `create_item`, `toggle_item` and `delete_item` are sync `#[tauri::command]`s, so they
  run on the main thread.
- Every write goes through `mutate_items` → `snapshot_storage`. That path:
  - fsyncs a diagnostics log entry;
  - counts captures;
  - runs a full SQLite `backup_to`, a `validate_database` and a `sync_all` on the
    backup copy.

  This is why each write takes about 20 to 40 ms and grows with database size.
- `QueueItem` is not memoized. Each composer change re-renders every queue row, which
  costs about 19 ms of React commit at 300 rows.
- Each `focus` triggers a full `snapshot_queue` refresh plus `permission_status`.
